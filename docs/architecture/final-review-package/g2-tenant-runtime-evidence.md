# G2 tenant runtime evidence

**Status:** Open — partial implementation evidence only. This record does not close G2 or authorize tenant business tables/modules.

**Verification authorization:** The Chairman authorized the CTO to coordinate and complete the remaining G2 verification on 2026-11-07. See [Chairman G2 verification authorization](chairman-g2-verification-authorization.md). This does not constitute G2 acceptance.

## Completed

- The local `dawineks_runtime` login connects to `dawineks_hospitality_os` as a non-owner and without superuser, role-creation, database-creation, or RLS-bypass attributes. The separate owner role is `dawineks_owner` (NOLOGIN).
- Runtime has database CONNECT and public-schema USAGE, but no public-schema CREATE privilege.
- A read-only role/schema review in pgAdmin on the local PostgreSQL 18 database (2026-11-08) confirmed `dawineks_owner` is NOLOGIN with no superuser, create-database, create-role, or RLS-bypass attributes; `dawineks_runtime` is LOGIN with the same elevated attributes false and no inherited roles. Runtime has `public` USAGE but not CREATE, and has neither USAGE nor CREATE on `tenant`; it has `g2_proof` USAGE but not CREATE. Only the owner and runtime application roles with the `dawineks_` prefix are present; no migration login exists. The `tenant` schema currently contains no tables. This is local least-privilege evidence, not a production or migration-role grant review.
- Added transaction-scoped tenant context that requires valid account/property UUIDs and a 256-bit signing key. The middleware uses the authenticated principal and account/property selection hints to resolve an active membership server-side; PostgreSQL RLS limits the membership lookup to that principal. The lookup and downstream tenant work share one transaction, so membership revocation cannot race between authorization and tenant access. Client headers are not trusted.
- Configured Laravel's user model to generate non-incrementing UUIDv7 identifiers, matching the UUID principal boundary used by the tenant context.
- Added isolated PostgreSQL proof fixtures with forced RLS, account/property scoping, a security-invoker view, a signing-key table unavailable to the runtime login, and a deny-by-default invalid-context function.
- Added automated PostgreSQL tests for role separation, forced RLS, default denial, account/property boundaries, security-invoker views, transaction cleanup, and forged settings; added a PostgreSQL 15–18 CI workflow and a tenant-table RLS coverage guard.
- Local checks completed: PHP syntax checks and Pint passed. The focused middleware test `test_client_supplied_tenant_headers_do_not_create_server_context` passed (1 test, 1 assertion).
- The test-only proof fixture and a random local signing key are installed in the application database; the key is kept in the local ignored `.env` and is not part of the repository.
- The local PostgreSQL feature suite passed as `dawineks_runtime`: 7 tests, 29 assertions. It covers non-owner/no-bypass role attributes, forced RLS, deny-by-default reads/writes, account/property isolation on the table and security-invoker view, transaction cleanup and rollback, rejected client headers, forged custom settings, inaccessible signing-key material, and reuse of the same PostgreSQL backend after context success and failure.
- The rollback-failure path now calls Laravel's connection-manager purge for the affected connection. Its focused test passed: 1 test, 8 assertions. This verifies the purge is requested when rollback fails; a real PostgreSQL reset failure and connection eviction are not simulated by this unit test.
- The tenant-table coverage guard executed successfully against the live PostgreSQL 18.6 database (318 ms). The `tenant` schema currently has no tables, so this verifies guard execution only, not business-table policy coverage.
- Combined verification passed: 8 tests, 37 assertions. The current installed PHP runtime lacks `pdo_pgsql` and `mbstring`; the suite was run with matching PHP 8.5.12 NTS x64 modules loaded temporarily for the test process. No PHP installation or system configuration was changed.

- The identity tables, production principal/tenant verifier, and membership resolver are exercised in CI, but authentication-provider wiring, real user sign-in, password-reset and credential handling, MFA, and POS device-enrollment flows are not implemented or evidenced. Hosted CI verifies the migration role and grants in a disposable database; production provisioning and a production grant review remain unqualified. The local-only workspace preview route is protected and tested, but Filament, Livewire, API, export/file, queue/schedule, Octane, pooled-connection checkout/release, and broader error/retry paths required by G2 remain unverified. The backend-PID check proves reuse of one PostgreSQL session across test operations, not behavior of an external connection pool or long-lived worker.
- External connection-pool checkout/release and long-lived worker behavior remain untested. The real PostgreSQL session-loss test verifies eviction and replacement through Laravel's connection manager in the disposable CI database.
- No separate migration login or full production grant review has been qualified.

## Claude Code review and remediation status (2026-11-08)

The Chairman supplied Claude Code's review of commit `4431f3e` in the active work thread. It is recorded as an AI security review with disclosed limits, not as a human review or independent human acceptance. The report rejected G2 at that commit and identified findings F-1 through F-7 plus stale evidence. Because no human reviewer is currently available, no human countersignature is claimed; G2 remains open pending evidence and formal acceptance.

Follow-up implementation and hosted verification:

- **F-1, tenant membership enforcement:** addressed in the production identity migration. PostgreSQL now validates the authenticated principal signature, account/property signature, current transaction ID, and active identity membership. The isolated tenant-table proof fixture delegates to those same production security functions. Hosted run [#42465257631](https://github.com/Kelvinnyachae/HotelPMS_POS/actions/runs/42465257631) passed all configured PostgreSQL 15–18 jobs.
- **F-2, identity-table RLS and migration separation:** moved into the versioned migration, with forced RLS, owner/runtime policies, a non-superuser migration login, and immediate post-migration grant/ownership assertions. The same run passed these checks in all four PostgreSQL jobs.
- **F-3, integration evidence:** the workspace preview now applies authentication and tenant-context middleware on the actual route, and a routed feature test confirms the resolved context is cleared afterward. Run [#42469490743](https://github.com/Kelvinnyachae/HotelPMS_POS/actions/runs/42469490743) passed all four PostgreSQL jobs. This is partial progress; the future application surfaces and worker/pool integration remain open.
- **F-4, request exception rollback:** the tenant transaction now rolls back when Laravel returns an error response; a routed failure test was added in commit `228a3ac` and passed in hosted run [#42464072331](https://github.com/Kelvinnyachae/HotelPMS_POS/actions/runs/42464072331). Streamed-response/export context remains unverified because those surfaces do not exist yet.
- **F-5, session-level context leakage:** tenant and principal signatures are bound to `txid_current()` and request context uses transaction-local settings. The PostgreSQL 15–18 tenant isolation matrix passed in run #42465257631.
- **F-7, exposed fixed CI key:** removed the literal workflow key and generate an ephemeral random key for each CI job. Run [#42465494070](https://github.com/Kelvinnyachae/HotelPMS_POS/actions/runs/42465494070) passed all four PostgreSQL jobs. Production still uses a shared application/database key and has no demonstrated rotation procedure; this part of F-7 remains open.

Still open from the review: **F-3**, application-wide integration beyond the single protected preview route (future Filament/Livewire/API, exports, queues, schedules, Octane and external pool behavior); **F-6**, production sign-in, password reset, MFA, POS device enrollment and identity access design; and production key separation/rotation under **F-7**. No tenant business tables or tenant modules were authorized or added by these remediations.

## Disposition

G2 remains **Open / not passed**. The Claude Code report rejected the reviewed commit; later CI evidence addresses parts of its findings but is not a new independent security acceptance. Tenant business tables and tenant-scoped modules remain blocked pending the missing integration, production-grant, key-rotation, identity-flow, and formal review/acceptance evidence listed in `implementation-gates.md`.
